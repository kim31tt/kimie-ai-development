# KIMIE | Chat & Todo — 複数ユーザー版

Supabase Auth + PostgreSQL/RLSで、ログインユーザーが案件・会話・Todoを共有します。フロントエンドはES modulesをesbuildでバンドルし、Vercelで配信します。

このブランチは本番切り替え準備です。Supabaseプロジェクト、メール送信、Vercel環境変数の設定後に実環境で確認してmainへ統合します。公開中の試作版のブラウザ保存データは自動送信・移行しません。

## 利用の流れ

1. メールの確認コードでログイン・登録し、表示名を登録。
2. 初回管理者は組織と案件を作成。招待されたユーザーはメールアドレス照合で所属が追加されます。
3. 管理者が「メンバー・招待管理」でカテゴリ（自社／取引先／施主／その他）と参加案件を指定して招待登録。アプリURLを相手に共有します。招待メール自体の自動送信はありません。
4. 案件内の参加者を選びチャット開始。同じ組み合わせなら既存チャットを再利用します。
5. 会話から相談・依頼・返答待ちをルールでTodo候補に登録。小タスク、複数担当、予定日、期限、待ち原因、優先度、メモを編集できます。

## 権限・保存

- ユーザーの識別はSupabase AuthのUUID。表示名は識別子ではありません。
- 組織・案件・会話の参加者を別々に管理。管理者も、参加していない会話の本文・Todoは取得できません。
- 全9テーブルにRLS。クライアントはSELECT権限だけを持ち、変更は認証・権限・整合性を検証するトランザクションRPCに集約。
- 招待は確認済みメールアドレスと一致し、有効期限内・未取消の場合のみ受理。認証アカウントの作成だけで既存組織の権限は得られません。
- 投稿者はサーバーの認証IDから設定。同じ送信IDの再送は重複登録せず、Todoの同時編集はversionで競合検出。
- 共有情報はサーバーに保存。ブラウザ内には認証セッションを保持します。下書きはメモリのみで、ログアウト・再読み込みで消えます。
- 画面が表示中は15秒間隔で更新（ダイアログ編集中は待機）。WebSocket即時配信は未実装です。

## 開発・検証

Node.js 24推奨。

```sh
npm ci
npm run check
cp .env.example .env.local
# .env.localに公開接続情報を設定
npm run dev
```

- `npm run check`: 構文、旧モデル回帰テスト、実Postgresエンジンを使ったDB/RLSテスト、本番ビルド。
- `tests/database.test.mjs`: PGlite上で認証ロールを切り替え、アクセス拒否・招待・参加解除・二重投稿・同時編集を検証。実際のSupabase Auth/SMTPの代替にはならないため、接続後に実アカウント検証が必要です。
- `node scripts/test-server.mjs`: ローカルUI検証専用。ループバックに限定した一時DBと疑似認証を使い、メールは送信しません。テスト用ユーザーとコードは起動時に表示されます。デプロイには使用しません。
- 配信対象は`dist/`のみ。旧`app.mjs`・`model.mjs`・`index.html`は試作版の回帰確認用で、本番バンドルには含まれません。

## 公開切り替え

[設定手順](docs/PRODUCTION_SETUP.md)を実施してからmainへ統合します。BのActionsでテスト成功後、Aへ同期し、Vercelが`dist/`を配信します。Aへ`.github`は同期しません。接続先未設定の本番ビルドは失敗させ、ログインできない版への置き換えを防ぎます。

## アプリ一覧とURL

トップ `/` はKIMIE AI Developmentのアプリ一覧です。Chat & Todoは `/chat-todo/` に配置し、アプリ内の「アプリ一覧」またはKIMIEロゴからトップに戻れます。ログイン後の権限は引き続きSupabaseで検証します。

アプリの追加時は専用ディレクトリを作成し、`apps.mjs` の一覧に名前・説明・URL・タグを登録します。入口は同じタブで開きます。トップページはログイン権限を付与せず、各アプリ側で権限を検証します。
